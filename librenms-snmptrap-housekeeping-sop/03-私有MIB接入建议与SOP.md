# 私有MIB接入建议与实践操作SOP（基于当前环境真实核验，2026-07-17）

> 本文档整合自实际操作过的两个真实案例（iKuai爱快、H3C），以及今日对代码/配置的重新核验结果。
> 不重复贴长篇原理讲解，聚焦于"接下来接入新厂商私有MIB时该怎么做"的可执行清单，
> 并标注每一步为什么要这样做（避免变成"照抄不理解"的操作手册）。

## 1. 接入私有MIB前，先回答三个问题

### 1.1 目标设备到底需不需要私有MIB？

先查官方标准MIB（`IF-MIB`等）能否覆盖需求。真实案例：H3C接口闪断/up-down监控完全依赖
标准`IF-MIB`，跟H3C私有MIB毫无关系，官方开箱即用，**不需要**导入私有MIB、不需要开发Handler。

私有MIB真正需要解决的是"标准MIB无法覆盖的、厂商自定义的对象"——比如设备特有的CPU/内存/温度
数值型OID、厂商自定义的故障类trap（风扇异常、电源异常、ARP表满等）。

**⚠️ 规范要求：接入私有MIB前先明确"要监控的具体指标是什么"，不要为了"看起来完整"
而无差别导入整份厂商MIB包再全量适配，这是本环境H3C案例踩过的教训——H3C私有MIB里
有大量trap定义本身存在解析缺陷，全量`-m ALL`加载会导致每次trap都产生大量警告日志
（详见《02-Housekeeping实践与建议》第2节）。**

### 1.2 是轮询数据（polling）还是主动上报（trap），还是两者都要？

这决定了接入路径完全不同：

- **只需要轮询数据**（设备被识别为正确类型、能采集CPU/内存/接口等指标）：
  只需要做设备识别适配（OS detection/discovery + 图标），**不需要**动`snmptrapd`、
  不需要开发Trap Handler。iKuai目前就是这种情况——"iKuai不会发trap，只需要轮询节点数据正常"。
- **需要接收设备主动发送的trap**：除了上面的识别适配，还需要确保`snmptrapd`能加载对应MIB
  （翻译OID），以及考虑是否要为具体trap开发专属Handler（提取数值、判断阈值）。

### 1.3 私有MIB文件本身质量如何？

拿到MIB文件后先做静态检查（工具见第2节），不要假设厂商提供的MIB文件本身没有问题。
真实案例：iKuai和H3C的私有MIB都存在`notifications`节点定义缺陷，
在当前net-snmp版本下无法被正确解析，会在每次trap到达时产生警告（但不影响其他正常OID的解析）。

## 2. 接入操作步骤（分两条路径）

### 路径A：仅轮询数据识别适配（如iKuai场景）

#### Step 1：MIB文件问题诊断与修复

拿到厂商MIB文件后，先用`snmptranslate`/`snmpwalk`等工具（或直接跑一次`snmptrapd -f`观察启动日志）
检查是否有语法错误、依赖缺失的引用。真实操作参考：`ikuai-mib-adaptation-sop` Step2记录了
完整的诊断修复过程，包括修正MIB文件里的语法问题。

#### Step 2：编写设备识别定义文件

需要在`resources/definitions/os_detection/<厂商>.yaml`和`os_discovery/<厂商>.yaml`
里定义识别规则（通常基于`sysObjectID`或特定OID匹配）。真实文件位置（当前环境）：

```
./custom-os-definitions/os_detection/ikuai.yaml
./custom-os-definitions/os_discovery/ikuai.yaml
```

#### Step 3：图标资源

放一张图标文件（PNG格式），真实路径（当前环境）：

```
./custom-icons/ikuai.png  ->  容器内 /opt/librenms/html/images/os/ikuai.png
```

#### Step 4：持久化挂载（⚠️ 最容易漏做、最容易返工的一步）

**这是本环境此前真实踩过的坑，必须按下面的方式做，不要用`docker cp`临时写入：**

```yaml
# librenms 主容器 和 dispatcher 容器都需要挂载（snmptrapd不需要，见下方说明）
volumes:
  - "./custom-icons/ikuai.png:/opt/librenms/html/images/os/ikuai.png:ro"
  - "./custom-os-definitions/os_detection/ikuai.yaml:/opt/librenms/resources/definitions/os_detection/ikuai.yaml:ro"
  - "./custom-os-definitions/os_discovery/ikuai.yaml:/opt/librenms/resources/definitions/os_discovery/ikuai.yaml:ro"
  - "./librenms/mibs/ikuai:/opt/librenms/mibs/ikuai:ro"
```

**⚠️ 规范要求：**
- 图标和识别定义文件必须用**独立的bind mount精确挂到镜像内部具体路径**，
  直接`docker cp`写入容器内部文件系统不会持久化，容器重建或`docker compose up -d`
  重建对应服务时会丢失。
- `librenms`主容器和`dispatcher`容器**都要挂**——`dispatcher`是真正执行poll轮询、
  每次poll都会重新调用`findOsImage`判定图标的容器，漏挂这一条会导致每次poll把图标
  重新判定为"文件不存在"，覆盖回默认的`generic.svg`（真实踩过的坑）。
- `snmptrapd`容器**不需要挂**图标和识别定义文件——`snmptrapd`进程本身不判断设备OS类型、
  不渲染图标，这是有意的差异，不是遗漏，如果新人看到`snmptrapd`挂载列表比另外两个容器少，
  不要假设这是配置错误。

#### Step 5：验证识别结果

触发一次discovery，检查设备的`os`字段是否变成了厂商标识（而非`generic`），
以及轮询数据是否正常入库。

### 路径B：额外需要Trap接收能力（如需要为私有MIB开发专属Handler时）

在完成路径A的基础上，额外需要：

#### Step 1：确保MIB目录被`snmptrapd`加载

通过`.env`的`SNMP_EXTRA_MIB_DIRS`环境变量追加路径（`:`分隔多个厂商目录），
`snmptrapd`容器的`environment`里引用该变量，容器启动时会拼进`-M`参数。
真实验证方式：

```bash
docker exec <snmptrapd容器> ps aux | grep snmptrapd
# 确认 -M 参数里包含新增的厂商目录路径
```

MIB文件本身走独立的`volumes`挂载放到磁盘上持久化（可以是独立挂载，也可以放进已有的
大挂载范围内，见下方"两种持久化模式"）。

#### Step 2：模拟发送trap验证MIB翻译能力

用`snmptrap`命令行工具模拟发送一条trap，观察`snmptrapd`日志（stdout）里OID是否被
正确翻译成`MODULE::name`形式的文本，而不是停留在纯数字OID。

**🔍 排障参考**：如果翻译失败，先检查是不是MIB文件本身语法有问题（Step 1路径A的问题），
而不是默认假设是环境配置问题。

#### Step 3：判断是否需要为具体trap开发专属Handler

只有当默认的Fallback处理（只记录OID名字，无数值提取）不满足需求时，才需要开发专属Handler。
需要同时修改（详见《01-SNMPTrap接收数据链路》第2.4节的代码级说明）：

- `config/snmptraps.php`的`trap_handlers`数组，新增`'MODULE::oidName' => Handler类::class`映射
- `LibreNMS/Snmptrap/Handlers/`目录，新增对应Handler类文件，实现`SnmptrapHandler`接口

**⚠️ 规范要求（本次核验代码后确认的关键结论）：这两处修改都是直接改LibreNMS镜像内部文件，
官方在`config/snmptraps.php`文件头部明确写"DO NOT EDIT THIS FILE"，且没有提供额外的
配置合并/覆盖机制（不是Laravel标准的多文件config合并场景）。这意味着这类改动只有两种
持久化方式，必须二选一，不能像图标/识别定义那样简单bind mount单个文件：**

1. **Fork源码管理**：把整个LibreNMS源码（或至少`app/`、`LibreNMS/`、`config/`相关部分）
   纳入自己的版本管理，基于官方版本打补丁，升级时手动合并。
2. **独立bind mount覆盖**：把改动后的`config/snmptraps.php`和新增的Handler文件，
   通过`docker-compose.yml`里的`volumes`逐个挂载到容器内部对应路径，覆盖镜像原始文件。

**本环境此前的真实失败案例：iKuai的3个专属Handler文件和`snmptraps.php`里对应的映射追加，
都是用`docker cp`直接写入容器内部文件系统，从未做上述两种持久化，
已在后续一次`docker compose up -d snmptrapd`容器重建中真实丢失。** 这是本SOP反复强调
"必须用bind mount或fork管理，不能用docker cp"的真实依据，不是理论上的担心。

#### Step 4：厂商隔离校验（多厂商环境下容易被忽视的一步）

如果环境里同时接入了多个厂商的私有MIB，Handler代码里如果用了较宽泛的OID前缀匹配逻辑，
可能会出现"厂商A的判断逻辑被厂商B的数据误触发"的情况。开发Handler时应该显式校验
`$device`的厂商/OS类型，而不是只看OID字符串本身。

#### Step 5：完整闭环验证

在不伪造网络身份的前提下，用真实设备或者受控的模拟发送（如`snmptrap`命令行工具指定
目标设备真实IP）验证完整链路：trap到达 → OID翻译 → Handler命中 → 数值提取 →
阈值判断 → 告警生成。

## 3. 两种MIB文件持久化模式的选择建议

真实案例对比（当前环境同时存在这两种模式，都验证有效）：

| 模式 | 适用场景 | 真实案例 | 优缺点 |
|---|---|---|---|
| 独立`volumes`挂载 | 需要覆盖/替换官方已有的单个文件，或者MIB文件较少、希望每个容器精确控制挂载范围 | iKuai：`./librenms/mibs/ikuai:/opt/librenms/mibs/ikuai:ro`，三个容器各自单独配置一遍 | 精确、显式，但容器一多需要重复写多份配置 |
| 放入已有大挂载范围 | 一批新文件（不是覆盖官方文件），且多个容器已经共享同一个大的读写挂载点 | H3C：直接放进`./librenms:/data:rw`范围内，通过`SNMP_EXTRA_MIB_DIRS`环境变量指路径 | 更省事，新增厂商不需要改`volumes`列表，但依赖已有大挂载的权限范围（`rw`） |

选择依据：目标文件是"一批新文件"还是"要覆盖官方已有的单个文件"。iKuai的
`os_detection.yaml`必须用独立bind mount精确覆盖，因为它要替换官方镜像里原本没有
（或者官方有一份通用/错误识别版本）的具体文件路径；H3C的505个MIB文件是全新增量，
直接放进已有的`/data`大挂载范围更省事。

## 4. SOP标准动作清单

1. ⚠️ 接入前先确认真实需求（轮询/trap/两者），不要无差别全量适配整份厂商MIB包
2. ⚠️ 拿到MIB文件先做质量检查，不要假设厂商提供的文件没有问题
3. ⚠️ 图标、OS识别定义文件：`librenms`+`dispatcher`容器需要挂载，`snmptrapd`不需要
4. ⚠️ MIB文件本身：根据"覆盖单个文件"还是"新增一批文件"选择独立挂载或大挂载范围内放置
5. ⚠️ Trap Handler代码级改动（`config/snmptraps.php` + `Handlers/`目录新文件）：
   **禁止用`docker cp`直接写入容器内部**，必须用fork源码管理或独立bind mount覆盖，
   否则容器重建必然丢失（已有真实丢失案例）
6. ⚠️ 多厂商环境下，Handler代码要做厂商隔离校验，不能只靠OID字符串前缀判断
7. 🔍 排障参考：怀疑私有MIB相关功能"突然失效"，先核实是不是最近发生过一次容器重建，
   再核实该功能当初是走哪种持久化方式做的（配置文件/图标/MIB文件 vs Handler代码）
8. 🔍 排障参考：判断"当前环境处于什么状态"，禁止凭记忆下结论，必须逐项用实际命令核验
   （`docker ps`看容器组成、`mount`/文件存在性看真实挂载点、`ps aux`看进程真实参数、
   直接读文件/查数据库确认代码和配置内容）——这是本次核验（含本文档）遵循的方法论，
   也应该成为团队今后判断环境状态的标准方法
