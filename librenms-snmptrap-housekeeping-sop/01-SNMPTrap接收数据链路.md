# SNMP Trap 接收数据链路（基于当前环境真实核验，2026-07-17）

> 本文档所有结论均来自对当前测试环境（`lab-librenms` compose 项目）的实际命令核验，
> 不是照抄官方文档的理论描述。涉及具体文件路径、进程参数、代码片段的地方，
> 都是直接从容器内读取/执行得到的真实结果。

## 1. 整体链路总览

```
外部设备(iKuai/H3C等) --UDP/TCP:162--> snmptrapd进程(容器: lab-librenms-snmptrapd)
      --解析MIB，翻译OID--> snmptrapd.conf 里 traphandle default 指定的处理脚本
      --stdin管道--> /opt/librenms/snmptrap.php
      --构造Trap对象--> LibreNMS\Snmptrap\Dispatcher::handle()
      --按OID查表--> config/snmptraps.php 里 trap_handlers 映射
      --命中具体Handler / 或 Fallback兜底--> 执行handle()方法
      --按配置决定是否记录--> eventlog表 / 触发告警规则引擎(AlertRules::runRules)
```

## 2. 各环节真实配置核验

### 2.1 snmptrapd 进程启动参数（容器内真实进程）

```
/usr/sbin/snmptrapd -f -m ALL -M /opt/librenms/mibs:/opt/librenms/mibs/cisco:/data/mibs/ikuai:/data/mibs/h3c udp:162 tcp:162
```

- `-m ALL`：加载全部已知MIB模块名（不是只加载指定厂商）
- `-M <目录列表>`：MIB搜索路径，包含官方内置MIB目录 + Cisco专属目录 + 通过`SNMP_EXTRA_MIB_DIRS`环境变量注入的iKuai、H3C私有MIB目录
- 同时监听UDP和TCP的162端口

**⚠️ 规范要求**：`-M`参数的路径顺序和内容完全由`.env`里的`SNMP_EXTRA_MIB_DIRS`环境变量决定
（`docker-compose.yml`里`environment`区块拼接），新增厂商MIB时只需要在该变量后用`:`追加路径，
不需要改动`snmptrapd`容器的启动命令本身。

### 2.2 snmptrapd.conf（认证与分发配置）

```
disableAuthorization yes
createUser -e 0x1234567890 librenms_user SHA auth_pass AES priv_pass
authUser log,execute,net librenms_user priv
authCommunity log,execute,net lab_trap_community
traphandle default /opt/librenms/snmptrap.php
```

- 当前认证方式为SNMPv2c community字符串（`lab_trap_community`，值来自`.env`里的`LIBRENMS_SNMP_COMMUNITY`），
  同时保留了一个v3用户配置（`librenms_user`），但实际抓包验证的trap流量走的是v2c community。
- `traphandle default`表示所有trap（不区分具体OID）统一交给`/opt/librenms/snmptrap.php`处理，
  这是LibreNMS官方标准做法，不是本环境的定制。

### 2.3 snmptrap.php（PHP入口脚本，真实源码）

```php
#!/usr/bin/env php
<?php
use LibreNMS\Util\Debug;

$init_modules = [];
require __DIR__ . '/includes/init.php';

$options = getopt('d::');
if (Debug::set(isset($options['d']))) {
    echo "DEBUG!\n";
}

$text = stream_get_contents(STDIN);

// create handle and send it this trap
\LibreNMS\Snmptrap\Dispatcher::handle(new \LibreNMS\Snmptrap\Trap($text));
```

从`snmptrapd`收到的原始trap文本通过stdin管道传入，构造`Trap`对象后交给`Dispatcher::handle()`。

### 2.4 Dispatcher.php（路由核心逻辑，真实源码）

```php
public static function handle(Trap $trap): bool
{
    if (empty($trap->getDevice())) {
        Log::warning('Could not find device for trap', ['trap_text' => $trap->raw]);
        return false;
    }

    if ($trap->findOid('iso.3.6.1.6.3.1.1.4.1.0')) {
        // TrapOid未被正确翻译成文本，说明MIB没配对，直接记一条系统事件提示配置问题
        Eventlog::log('Misconfigured MIBS or MIBDIRS for snmptrapd...', $trap->getDevice(), 'system');
        return false;
    }

    $handler = app(\LibreNMS\Interfaces\SnmptrapHandler::class, [$trap->getTrapOid()]);
    $handler->handle($trap->getDevice(), $trap);

    $fallback = $handler instanceof Fallback;
    $logging = LibrenmsConfig::get('snmptraps.eventlog', 'unhandled');
    $detailed = LibrenmsConfig::get('snmptraps.eventlog_detailed', false);
    if ($logging == 'all' || ($fallback && $logging == 'unhandled')) {
        $trap->log($trap->toString($detailed));
    }
    if ($logging != 'none' || ! $fallback) {
        $rules = new AlertRules;
        $rules->runRules($trap->getDevice()->device_id);
    }

    return ! $fallback;
}
```

**关键机制解读（这是本环境此前排障过程中反复踩坑的核心原理）：**

1. **必须先找到`device`**：`$trap->getDevice()`如果找不到对应设备（发trap的IP没有在LibreNMS里被发现/添加为设备），
   直接记warning日志并return，**不会进入任何Handler处理，也不会写入eventlog表**。
   🔍 排障参考：如果怀疑trap没被处理，第一步应该确认发trap的设备IP是否已经是LibreNMS里的已知设备。

2. **OID必须被正确翻译**：如果`snmptrapd`因为MIB路径配置错误、MIB文件本身有问题导致OID没能从数字翻译成
   `MODULE::name`形式的文本，会命中`iso.3.6.1.6.3.1.1.4.1.0`这个判断（这是SNMPv2-MIB里snmpTrapOID.0的原始数字OID，
   说明连这个标准字段都没翻译成功），此时只记一条`system`类型的eventlog提示"MIB配置有问题"，**不会走到具体Handler**。

3. **Handler查找是精确字符串匹配**：`app(SnmptrapHandler::class, [$trap->getTrapOid()])`最终会走到
   `SnmptrapProvider::register()`里的这行核心逻辑：
   ```php
   $oid = reset($options);
   return $app->make(config('snmptraps.trap_handlers')[$oid] ?? Fallback::class);
   ```
   `$oid`是翻译后的完整字符串（如`IKUAI-MIB::sysCPUBusyGet`），去`config/snmptraps.php`的
   `trap_handlers`数组里做精确匹配，**匹配不到就退化为`Fallback`处理器**（只记一条`Log::info`，
   不做任何数值提取、不判断阈值、不做厂商隔离校验）。

4. **`config/snmptraps.php`文件头部写明"DO NOT EDIT THIS FILE"**：这是Laravel标准config文件，
   官方期望你通过环境变量或PR贡献代码来扩展，**没有提供额外的"合并/覆盖"机制**——也就是说，
   如果要给私有MIB的trap注册专属Handler，只有一条路：**直接改这个文件本身**，
   同时新增对应的Handler类文件到`LibreNMS/Snmptrap/Handlers/`目录。这个结论在
   `ikuai-trap-handler-sop` Step5（插件化方案调研）中已有过详细论证，本次核验代码后确认结论仍然成立。

5. **是否写eventlog、是否触发告警规则，由`snmptraps.eventlog`配置项决定**（当前为默认值`unhandled`，
   即只有走Fallback兜底的trap才会记eventlog；命中具体Handler的trap默认不重复记eventlog，
   因为Handler内部通常会自己决定要不要记录）。**告警规则引擎`AlertRules::runRules()`
   在trap命中具体Handler、或者`snmptraps.eventlog`配置不是`none`时都会被调用**——
   也就是说即便trap本身没有专属Handler，只要不是主动设置`eventlog=none`，
   每条到达设备的trap依然会触发一次告警规则引擎的判定（这解释了为什么此前housekeeping分析里，
   `eventlog`表的增长速率和trap到达频率大致对应）。

### 2.5 Handler层组织结构（真实统计）

```bash
docker exec lab-librenms-snmptrapd ls /opt/librenms/LibreNMS/Snmptrap/Handlers/ | wc -l
# 188
```

当前镜像内置188个官方Handler类文件，覆盖Alcatel/Cisco/Juniper/BGP等厂商和标准MIB的常见trap场景。
`Fallback.php`的真实实现：

```php
class Fallback implements SnmptrapHandler
{
    public function handle(Device $device, Trap $trap)
    {
        Log::info('Unhandled trap snmptrap', [
            'device' => $device->hostname,
            'oid' => $trap->getTrapOid(),
        ]);
    }
}
```

只写一条PHP日志（不是eventlog数据库记录），信息量仅有设备名和OID，没有任何数值提取。

## 3. 当前环境实际链路状态（2026-07-17核验）

| 检查项 | 结果 |
|---|---|
| snmptrapd进程是否运行 | ✅ 运行中（容器重建后已验证进程存活） |
| iKuai私有MIB是否被加载 | ✅ `/data/mibs/ikuai`在`-M`路径内 |
| H3C私有MIB是否被加载 | ✅ `/data/mibs/h3c`在`-M`路径内（505个文件） |
| iKuai专属Handler | ❌ 已丢失（此前用`docker cp`写入，未做持久化，容器重建后丢失） |
| H3C专属Handler | 未开发（目前所有H3C私有trap都走Fallback兜底） |
| iKuai/H3C私有MIB已知解析缺陷 | ⚠️ 存在，`notifications`节点定义有问题（`fan`/`power`/`slotTemperature`等），
每次trap到达都会触发全量MIB重新解析并打印大量`Cannot resolve OID`警告 |

**结论：当前环境里iKuai和H3C的私有trap，如果真实发生，都会退化为走Fallback兜底
（只记录OID名字，无数值、无阈值判断、无厂商隔离），因为专属Handler从未做持久化或从未开发。**

## 4. SOP标准动作清单

1. ⚠️ 新增厂商MIB目录：只需在`.env`的`SNMP_EXTRA_MIB_DIRS`追加路径，不改容器启动参数
2. ⚠️ 需要给某个私有MIB的trap开发专属Handler处理逻辑：必须同时修改两处
   - `config/snmptraps.php`的`trap_handlers`数组新增OID到Handler类的映射
   - `LibreNMS/Snmptrap/Handlers/`目录新增对应Handler类文件
   **这两处修改都是直接改镜像内部文件，官方没有提供配置合并机制，必须走fork源码管理
   或者独立bind mount覆盖才能持久化（见《03-私有MIB接入SOP》第4节）**
3. 🔍 排障参考：怀疑trap没被正确处理，按顺序排查：
   - 发trap的设备IP是否已被LibreNMS识别为设备（`getDevice()`第一道关卡）
   - OID是否被正确翻译成文本（不是走`iso.3.6.1.6.3.1.1.4.1.0`分支，说明MIB配置没问题）
   - 该OID是否在`config/snmptraps.php`里有精确匹配的映射（没有就是走Fallback）
   - 查`Log::info`级别的应用日志（不是eventlog表），Fallback处理的trap只在这里能看到记录
4. 🔍 排障参考：`snmptraps.eventlog`配置项默认值`unhandled`，只有Fallback处理的trap会记eventlog；
   如果需要所有trap（包括命中Handler的）都记eventlog，可以调整该配置为`all`
